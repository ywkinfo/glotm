# 다중 포럼 집행 오케스트레이션과 병행 트랙 운영

영국 상표 집행은 하나의 침해 사건이 여러 포럼에 동시에 걸치는 경우가 많다. 같은 seller가 marketplace에 위조품을 올리면서 `.uk` 도메인을 선점하고 국경을 통해 물량을 들여오면, 플랫폼 신고·Nominet 분쟁·HMRC 국경조치·UKIPO Tribunal·법원 검토가 한꺼번에 필요해진다. 각 포럼을 다루는 장(제10장 집행·분쟁, 제11장 플랫폼·도메인, 제12장 세관, 제06장 opposition·tribunal)이 "어떻게 하나"를 설명한다면, 이 장은 그 트랙들을 **동시에 어떤 순서로, 누가, 어떤 속도로 굴릴지**를 정하는 오케스트레이션 레이어다.

핵심은 개별 포럼 지식이 아니라 조정이다. 트랙마다 owner·속도·선행조건·증거 요구가 다르기 때문에, 조정 없이 각 팀이 따로 움직이면 증거가 엇갈리고 진술이 충돌하며 기한을 놓친다. 이 장은 단일 사건 보드 위에서 병행 트랙을 정렬하는 판단 프레임과 구조화 산출물을 제공한다.

## 단일 사건이 다중 포럼으로 번지는 신호

먼저 "이 사건은 한 트랙으로 끝나는가, 여러 트랙을 동시에 열어야 하는가"를 판별한다. 아래 신호가 둘 이상 겹치면 병행 오케스트레이션 대상으로 올린다.

| 신호 | 추가로 열리는 트랙 | 왜 동시 대응인가 |
| --- | --- | --- |
| 같은 상대가 여러 marketplace에 반복 출현 | 플랫폼 + IPEC | 개별 listing 삭제만으로는 재출현을 못 막음 |
| 위조품에 안전·건강 위험 동반 | 세관(AFA) + 플랫폼 + 법원 | 물량 유입 자체를 국경에서 끊어야 함 |
| 침해자가 `.uk` 도메인·계정까지 선점 | Nominet DRS + 플랫폼 | 브랜드 검색 유입을 가로채는 별도 피해 |
| 유통 파트너의 계약 위반 + 잔존 사용 | 계약 집행 + tribunal/법원 | 계약 트랙과 권리 트랙을 분리해야 함 |
| 상대가 먼저 opposition·revocation을 걸어옴 | UKIPO Tribunal + 집행 | 방어와 공격 트랙을 같은 보드에서 봐야 함 |

## 병행 트랙 매핑

병행 대응으로 판단되면, 열려 있는 트랙을 한 표에 올려 owner·속도·구제·선행조건을 명시한다. 이 매핑이 오케스트레이션의 기준선이다.

| 트랙 | 대표 포럼 | 속도 | 얻는 구제 | 선행조건 |
| --- | --- | --- | --- | --- |
| 플랫폼 takedown | marketplace 신고 채널 | 24-48시간 | 개별 listing 삭제 | 증거 스크린샷 + 권리 근거 |
| 국경조치 | HMRC UK Application for Action | 사전 신청 필요 | 의심 화물 detention | 최소 30 working days 전 신청 권장 |
| 도메인 분쟁 | Nominet `.uk` DRS | 수주 단위 | 도메인 이전·취소 | abusive registration 근거 |
| 소액·간이 소송 | IPEC small claims | 수개월 | 저가치 침해 구제 | £10,000 이하 분쟁 적합 |
| 본안 소송 | IPEC multi-track / High Court | 수개월-1년+ | damages·injunction | 사실관계·증거 정리 완료 |
| 등록 분쟁 | UKIPO Tribunal | 절차 기간 고정 | opposition·revocation 결과 | TM 서식·기한 준수 |

병행 트랙은 전부 동시에 최고 속도로 굴리는 것이 목적이 아니다. 국경조치처럼 **사전 신청 리드타임**이 있는 트랙은 먼저 걸어 두고, 플랫폼 takedown처럼 즉시 효과가 나는 트랙으로 급한 확산을 끊은 뒤, 법원·tribunal 같은 느린 트랙은 증거가 정리된 뒤 진입한다.

## 트랙 간 순서와 충돌 관리

병행 대응의 실패는 대부분 포럼 지식이 아니라 트랙 간 정합성에서 온다. 아래 두 축을 먼저 잠근다.

### 증거 일관성

같은 사건인데 플랫폼 신고에는 A 증거, tribunal에는 B 증거, 법원에는 C 증거를 따로 만들면 상대가 불일치를 파고든다. 하나의 증거 팩(제08장 사용증거·제10장 dispute quick pack과 연결)을 만들어 모든 트랙이 같은 원본을 참조하게 한다.

| 증거 항목 | 어느 트랙이 쓰나 | 정합 포인트 |
| --- | --- | --- |
| infringing use 원본 캡처 | 플랫폼·IPEC·tribunal | 캡처 일시·URL을 트랙 간 동일하게 |
| 권리 근거(등록번호·owner) | 모든 트랙 | UK-only 권리 범위를 일관 표기 |
| 사용증거(자사 사용 실적) | tribunal·법원 | non-use 방어와 침해 주장이 모순되지 않게 |
| 피해·확산 규모 | 법원·세관 | 구제 수준·긴급성 판단 근거 |

### 진술 충돌 회피

경고장, tribunal 서면, 협상 제안이 서로 다른 사실·요구를 담으면 사건 전체 신뢰도가 떨어진다. 트랙별 대외 메시지는 발신 전에 같은 사건 보드에서 교차 확인한다. 특히 협상 트랙에서 양보한 범위가 법원 트랙의 구제 요청과 모순되지 않도록 owner를 한 명으로 고정한다.

## 시점 동기화 캘린더

병행 트랙은 각자의 기한이 다르다. 이 기한을 하나의 캘린더에 올려 두지 않으면 빠른 트랙이 느린 트랙의 선행조건을 망가뜨린다.

| 트랙 기한 | 성격 | 오케스트레이션 메모 |
| --- | --- | --- |
| seller 확산 48시간 | rolling | 가장 먼저 끊되 증거 원본은 보존 후 삭제 요청 |
| HMRC AFA 30 working days | 사전 리드타임 | 시즌·캠페인 물량 전에 역산해 미리 신청 |
| opposition 공고 후 2개월 | 고정 기한 | 방어 트랙이 열려 있으면 최우선 캘린더에 고정 |
| cooling-off 초기 9개월(최대 18개월) | 협상 창구 | 협상 트랙과 tribunal 트랙의 속도를 이 창 안에서 조율 |
| 법원 준비 2주+ | 준비 의존 | 증거 정리 완료 신호가 뜨기 전 진입하지 않음 |

리드타임이 긴 트랙(국경조치)과 기한이 고정된 트랙(opposition)을 먼저 캘린더에 박고, rolling 트랙(플랫폼)을 그 위에 얹는 순서로 본다.

## 단일 트랙 유지 vs 다중 트랙 escalation gate

모든 사건을 다중 트랙으로 키울 필요는 없다. 오케스트레이션 비용 자체가 크기 때문에, 아래 gate로 트랙 확장 여부를 판단한다.

| 질문 | 단일 트랙 신호 | 다중 트랙 신호 |
| --- | --- | --- |
| 상대가 반복·조직적 침해자인가 | No | Yes |
| 피해가 한 채널에 국한되는가 | Yes | No |
| 국경·도메인 등 별도 피해 축이 있는가 | No | Yes |
| 내부에 트랙별 owner를 배정할 수 있는가 | 어려움 | 가능 |
| 조기 종료(합의)로 충분한가 | Yes | No |

다중 트랙 신호가 우세하면 아래 통합 보드를 개설하고, 그렇지 않으면 제10장 단일 사건 흐름으로 되돌린다.

## 통합 사건 보드 템플릿

병행 대응은 발견 당일 1페이지 통합 보드가 있으면 전체 속도가 달라진다. 아래 템플릿을 사건별로 채워 트랙을 한눈에 정렬한다.

| 필드 | 입력 예시 |
| --- | --- |
| 사건 ID / 발견일 | INC-2026-0xx / 발견 날짜 |
| 열린 트랙 | 플랫폼 · 세관 · Nominet · IPEC 중 해당 |
| 트랙별 owner | 각 트랙 담당(법무·사업·외부대리인) |
| 공통 증거 팩 위치 | evidence vault 링크 |
| 다음 기한 | 트랙별 가장 가까운 기한 |
| escalation 조건 | 무엇이 트리거되면 다음 포럼으로 |

## 트랙 종료·통합 판단

모든 트랙을 끝까지 끌 필요는 없다. 목적을 달성한 트랙은 닫고 자원을 남은 트랙에 모아야 사건 전체가 늘어지지 않는다.

| 트랙 상태 | 판단 | 액션 |
| --- | --- | --- |
| 목적 달성(삭제·이전 완료) | 종료 | 증거만 보존하고 닫음 |
| 협상 타결 | 통합 | 합의 조건을 다른 트랙 요구와 정합 |
| 반복·확산 지속 | 유지·상향 | 법원·세관 트랙으로 escalation |
| 비용 대비 실익 낮음 | 보류 | 모니터링으로 전환 |

## 사후 리뷰로 다음 사건 속도를 높인다

다중 포럼 사건이 끝나면 트랙별 소요·병목·재발 여부를 기록한다. 이 리뷰가 다음 사건의 초기 라우팅을 빠르게 만든다.

| 리뷰 항목 | 남길 것 |
| --- | --- |
| 트랙별 소요 시간 | 어디서 지연됐는가 |
| 증거 병목 | 어떤 자료가 늦었는가 |
| 진술 충돌 여부 | 트랙 간 메시지가 어긋났는가 |
| 재발 신호 | 같은 침해자·패턴의 반복 가능성 |

## 오케스트레이션 체크리스트

- 이 사건이 다중 포럼 신호(반복·별도 피해 축·선제 tribunal)를 충족하는지 판별했는가
- 열린 트랙을 owner·속도·구제·선행조건 표로 매핑했는가
- 모든 트랙이 하나의 증거 팩 원본을 참조하도록 정합시켰는가
- 경고장·tribunal 서면·협상 제안 사이 진술 충돌을 교차 확인했는가
- 리드타임 트랙(AFA)과 고정 기한 트랙(opposition)을 캘린더에 먼저 고정했는가
- 통합 사건 보드에 트랙별 다음 기한과 escalation 조건을 적었는가
